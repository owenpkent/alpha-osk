# Privacy mode and password detection

This document holds the full write-up behind the CLAUDE.md section *Privacy Mode & Password Detection*, including its subsection on clearing stale typing context (which has its own deeper doc, `CONTEXT_RESET.md`).

## Privacy Mode & Password Detection

Protects sensitive input (passwords, PINs) from leaking into the prediction model.

### How it works
- **Auto-detection** (Windows): two complementary paths, both answered from the focus probe's readings (below):
  1. A background `QTimer` polls every 200ms (`_check_password_field`). Catches focus changes that happen between keystrokes.
  2. **Every keystroke** (`pressKey`/`pressSpecialKey`) also calls `_check_password_field_sync()`. Closes the race window where the first characters after focus lands on a password field would otherwise reach the prediction cache before the timer fires. A stored reading under `_FOCUS_READING_FRESH_S` (50 ms) old answers it outright; otherwise it asks the probe for a fresh one and waits at most `_FOCUS_REQUEST_TIMEOUT_S` (25 ms). On Linux and macOS there is no probe and both paths call `is_password_field()` directly, the keystroke one rate-limited to ~50 ms via `_last_sync_password_check`.
- **The keyboard thread never calls UI Automation (since 2026-11-03).** `src/platform/focus_probe.py::FocusProbe` is a daemon thread that builds the detector on itself (`password_detect.start_focus_probe`, Windows only; its own COM apartment and UIA connection) and takes one `FocusReading` (foreground window, focused element's RuntimeId, `IsPassword`, `read_at`, `seq`) about five times a second and whenever `request()` asks, from one `GetFocusedElement` (`_WindowsUIADetector.read_focus`). Before it, a target slow to answer UIA held the keystroke that asked: Thunderbird was measured at 317 ms per call, and two separate questions (password at 5 Hz, element at 4 Hz) asked it twice. Now a stalled target costs a keystroke 25 ms. **The wait is bounded, not the probe**: a stalled COM call cannot be interrupted, so while the target stalls every request inside the stall comes back `None`, the key goes out on what was known, and the late reading is applied when it lands. Learning happens only when a word finishes (space, pill, Save), seconds later, by which time the answer is in; the worst case is a stall that spans a whole word, bounded by the UIA transaction timeout below, which is why the deferred-learning variant was not built (the owner's call, 2026-11-03).
- **Every reading reaches the bridge on the UI thread through `_FocusNotifier.reading`, a queued connection** (`_on_focus_reading`), the prediction loader's pattern: the probe thread mutates nothing on the bridge. The polls read `latest()`. **A reading taken under another foreground window is dropped** (`_apply_focus_reading`): it says nothing about the window in front now, and the next reading settles it. **A reading older than the last context reset says nothing about the focused element** (`_focus_reading_floor`, strict, since `time.monotonic` ticks every 15.6 ms on Windows under 3.12): the stored one still names the field Tab just left, and seeding from it would have brought back `hellis` (`CONTEXT_RESET.md`). The churn grace judges a reading by its own `read_at`, not by when the poll got round to it (`_typed_within_focus_grace(at=...)`).
- **Shutdown stops the probe first** (`FocusProbe.stop`, bounded join): the detector closes on the probe thread, in the apartment that created it, and after `stop` no reading is delivered even if the thread is still inside a call. **Tests never start the real thread**: `tests/conftest.py::_unplug_the_live_desktop` stubs `start_focus_probe` to `None` (the direct path, with `is_password_field` stubbed), and `tests/test_focus_probe.py` patches it with a probe over a fake detector that can stall: a keystroke returns inside the budget, a late "password" answer still switches privacy mode on, an answer for the wrong window is ignored, a reading older than a reset does not seed, and shutdown leaves no thread.
- Detection uses Windows UI Automation COM (`IUIAutomation::GetFocusedElement` -> `UIA_IsPasswordPropertyId`) in native apps and browsers. Falls back to Win32 `EM_GETPASSWORDCHAR` if UIA fails.
- **No probe may wait on another process without a bound.** The Win32 fallback sends `EM_GETPASSWORDCHAR` with `SendMessageTimeoutW` (`SMTO_ABORTIFHUNG`, 100 ms), never `SendMessageW`: a plain send to a hung app (Resolve, Acrobat, Premiere Pro) never returned, and Windows closed the keyboard as hung (`AppHangXProcB1` in the Application event log). A timeout reads as "not a password field". That was written when the probe ran on the UI thread; on the probe thread an unbounded wait would stall every reading after it instead, which is the same keystroke held by another road. Test: `tests/test_password_detect.py::TestTheWin32ProbeNeverHangsTheKeyboard`.
- **UIA must accept the apartment it finds.** The probe thread initialises its own (`CoInitializeEx(COINIT_MULTITHREADED)`, S_OK, so it owns and uninitialises it). The detector also still starts on the UI thread (tests, and the direct path): Qt's Windows platform plugin initialises that thread as an STA, so the same call returns `RPC_E_CHANGED_MODE`; that means "COM is ready, not yours to uninitialise", not failure. Until 2026-10 it was treated as failure and every real launch logged `Password detection: Windows Win32 fallback`, which cannot see browser password fields and gives `focused_element_token` nothing to report. The headless tests ran on the offscreen platform, which leaves COM alone, so they never saw it.
- **Every UIA call is bounded**: the detector is `CUIAutomation8` as `IUIAutomation2` with 250 ms connection and transaction timeouts (defaults 2 s and 20 s); without them it refuses UIA rather than risk a freeze. One frozen app therefore cannot hold up every probe reading after it for long. It also skips the query when the foreground window is hung (`IsHungAppWindow`) or our own (a UIA client querying its own UI thread can deadlock). Tests: `tests/test_password_detect.py::TestUIAStartsUnderQt`, `::TestUIASkipsWhatCannotAnswer`.
- **`UIA_IsPasswordPropertyId` is a `VARIANT_BOOL`: read the low 16 bits only** (`variant.val & 0xFFFF`). The local `_VARIANT` exposes the union as one 64-bit `val`, and UIA leaves the bytes above the bool as it found them: Explorer's XAML input sites (taskbar, Start, search; class `Windows.UI.Input.InputSite.WindowClass`) answer "false" as `0x00007ffa37780000`. Comparing all 64 bits with zero read those as password fields. The bug was latent until UIA started in the real app (1.9.1, the apartment fix above); from then privacy-mode flips in the log went from under 15 a day to 150 to 350 a day, each about 200 ms long. Every flip suppresses the punctuation auto-space (that branch of `_press_char` runs only outside privacy mode) and scrubs the typing context, so the user saw it as auto-spacing and suggestions dropping out at random, not as a privacy problem. Fixed in 1.9.4 (#223). Test: `::TestUIAReadsOnlyTheBool`.
- **Diagnosing detection on a live desktop**: the log line `Password field detected` (INFO, no content) counts flips; a few a day is normal, hundreds is a false positive. To find the culprit, poll `_WindowsUIADetector` from a script outside the app and log the foreground exe plus the focused element's `ClassName`, `ControlType`, `FrameworkId` and the raw `IsPassword` VARIANT. Never read `Name` or `Value`: they can carry typed content.
- **Manual toggle**: the **Learning** switch in the title bar (static label + a sliding knob; accent when on, red when paused). Overrides auto-detection. Two earlier designs (a play/pause Canvas icon, then a text label that swapped between "Learning" and "Paused") both had to be read and interpreted; see the title-bar entries in `docs/architecture/GOTCHAS.md` for the full rationale.
- **When auto-detection has no working backend this session** (`detection_available()` in `password_detect.py`, surfaced read-only as `KeyboardBridge.passwordDetectionAvailable`): the null-detector fallback now logs a WARNING at startup instead of failing silently, and the UI says so in two low-key places rather than a dialog to dismiss: the Learning switch's tooltip appends "(auto-detect unavailable this session: this is your only protection)", and *Settings -> Data & Privacy -> Privacy* shows an amber note pointing at the switch. Detection fails open by design, so a backend that can never turn on still lets typing proceed; the manual toggle is the only thing between a password field and the model until it's fixed.
- **When active**: Keystrokes still reach the OS, but `_current_word`, predictions, and learning are all suppressed. The prediction bar shows "Learning paused".

### Clearing stale context when focus or the caret moves

Full write-up: `docs/architecture/CONTEXT_RESET.md` (section of the same name). Read it before changing this area.

Six signals reset the typing context, each catching what the others cannot: (1) foreground window, (2) focused element (UIA RuntimeId), (3) caret position, all polled at 4 Hz by `_check_foreground_window`; (4) a click outside our own process (`src/platform/pointer.py`, its own 50 ms poll); (5) Tab; (6) the `_NAV_KEYS`. **Stale `_current_word` / `_context_buffer` is not a bad suggestion, it is a pill tap that eats text elsewhere.**

- `None` from a token means "don't know" and leaves state untouched.
- **The outside click (4) resets mid-word; `_check_caret_moved` keeps its only-between-words guard. Don't re-unify them.** The old `_external_click_pending` deferral is deleted.
- Where a caret is published, a click is settled over `_CLICK_SETTLE_MS` (200 ms) against `_caret_before_click` (the previous tick's reading, never `_last_caret_token`); an unreadable caret resets. `_note_own_keystroke` sets both `_keystroke_since_poll` and `_keystroke_since_click_poll`, and it is set in the synth wrappers (`_send_key` / `_send_text` / `_replace_text`), not the keystroke entry points. `_reset_typing_context` clears a pending settle. A scrollbar click still resets.
- All three within-window resets pass `keep_snippet_offer=True`; an app switch and privacy mode withdraw the offer.
- **The tail of an interrupted word is never learned** (`_word_prefix_lost`, `_take_lost_prefix`). Tests for it must type the word three times.
- Own-window clicks are filtered by process id, not geometry. It polls rather than hooking, and reads **only the high bit** of `GetAsyncKeyState` (the low bit is system-wide and the read clears it for other assistive tools).
- Tab does not learn the word in progress (it is the accept-completion key). Delete and Escape are excluded from the nav-key reset. A held arrow resets once.
- `resetContext` (the slot behind the removed clear-context button) delegates to `_reset_typing_context`.
- Tests: `TestTabClearsContext`, `TestCursorMotionClearsContext`, `TestOutsideClickClearsContext`, `TestAnOutsideClickThatMovesNoCaretIsLeftAlone`, `TestCaretMoveClearsContext`, `TestAnInterruptedWordIsNotLearned`, `tests/test_pointer.py`.

### Key files
- `src/platform/focus_probe.py` - `FocusProbe` / `FocusReading`: the thread that owns the detector on Windows, its stored reading, and the bounded `request()`
- `src/platform/password_detect.py` - platform-specific detection (UIA COM via ctypes), `start_focus_probe`, plus `focused_element_token` / `caret_position_token`
- `src/platform/pointer.py` - `external_click_detected()`, the outside-click probe behind signal (4) above (Windows only, no-op elsewhere)
- `src/keyboard_bridge.py` - `_privacy_mode` flag, `_check_password_field()` timer, `_check_password_field_sync()` per-keystroke, `setPrivacyMode()` slot, `passwordDetectionAvailable` read-only property

### Linux
Auto-detection uses AT-SPI 2 via `gi.repository.Atspi`. A daemon thread owns a GLib event loop and listens for `object:state-changed:focused`; whenever focus lands on an accessible whose state set contains `STATE_PASSWORD_TEXT`, the shared `_is_password` flag flips on. Works for GTK (`GtkEntry` with `visibility=false`), Qt (`QLineEdit` in Password echo mode), and browsers that expose accessibility metadata. Requires `gir1.2-atspi-2.0` + a working at-spi bus on the host. If `gi` fails to import or `Atspi.init()` fails, falls back to the null detector and now logs a WARNING once at startup instead of failing silently (`detection_available()` surfaces this to the UI, see *How it works* above) - users can still toggle privacy mode manually.
